An ordinary OCaml value occupies one machine word and is either an immediate integer or a pointer. An individual float is represented by a pointer to a heap block: one header word with Double_tag followed by one 64-bit double payload on a 64-bit machine. The diagram is about the source-level value representation and calling/storage convention; a compiler may eliminate particular boxes when optimization proves that they are unnecessary. A float# has the float64 layout and is stored without a pointer, so it can be passed directly in a floating-point register or placed directly in a stack slot. SIMD vector types use the same unboxed-types mechanism with a vector layout. @ local constrains where a value may flow; stack_ is what forces where it is allocated. A heap value is accepted anywhere a local one is—so a @ local return type alone guarantees nothing.

Both lines allocate the same record type. The first record is returned, so it must survive make_points and lives on the GC-managed heap. The second allocation is explicitly marked stack_. It is used inside the function and reclaimed with the function's stack region. The type checker rejects returning local instead. Stack allocation is still allocation; it changes where the block lives and when its storage is reclaimed. The visible line is the part worth saying slowly, because I got it wrong in this parser. The mode and the allocation are separate decisions. Annotating a function's return type @ local restricts how the caller may use the value; it does not oblige the callee to build it on the stack, because a heap value satisfies a local requirement perfectly well. Five intermediate records in the number scanner—sign, digit run, integer part, fraction part, exponent part—were declared @ local without stack_, and were therefore heap-allocated. The parser measured allocation-free anyway, because inlining deleted the records before anything was allocated. Adding exclave_ stack_ to those five makes them allocation-free by construction instead of by luck. There is a backup slide with that experiment. This is the handoff from the simdjson primer to this project. simdjson-oxcaml deliberately exposes both contracts. Tape.Parser.parse is the borrowed benchmark-oriented API: Tape.t aliases parser-owned buffers and becomes invalid on the next parse using that parser. Parser.parse builds an ordinary owned Json.t: callers can retain it, pattern-match it, and parse another document independently. Both paths share the scanner and the underlying number, string, and grammar routines, so later comparisons isolate representation and allocation rather than comparing unrelated parsers. Point out the fused compare/movemask before reading the code: unlike the primer's two-step Int8x16.equal then movemask, the project's Int8x64.equal yields the 64-bit mask directly, which is why all_quotes and operator_mask flow straight into Int64_u operations. One Int8x64 block is an unboxed product of four int8x16# registers. Vector equality plus movemask identifies quotes. Prefix XOR turns quote positions into an inside-string mask. The individual masks are combined and string contents removed to produce one unboxed 64-bit structural mask. The right-hand mask begins with the same fifteen decisions highlighted in the running JSON example. Regular OCaml has neither these vector types nor these intrinsic operations. 2 · Inlining · result

Tactical inlining doubled throughput

≈ 2 → ≈ 4 GB/s26 inline-always annotations in the scanner + SIMD helper path

Still required under -O3: removing them costs 11–28% and puts allocation back into a zero-allocation path.

make_group_mask was one instance, not the whole fix. Twenty-six inline-always annotations across the scanner, SIMD helpers, block loader, and iterator removed the call boundaries and let the compiler optimize the loop end to end. For an audience used to C++ and LLVM, the surprising part is how much explicit inlining guidance was required. The obvious objection is whether an optimization preset would have done this for free, so I measured it. It would not. Under -O3 with the annotations deleted, the parser loses eleven to twenty-eight percent depending on path and fixture, and—more tellingly—the reusable tape path goes from zero allocated words per parse to about a hundred and nine thousand on numbers.json. Output A · borrowed tape

Borrowed tape peaks at 1.2 GB/s

1.2 GB/sreusable borrowed tape · 0 allocated words

0 minor and 0 major words on all seven fixtures—measured. [@zero_alloc] covers the leaf helpers; the composed public path is not annotated, so the property is observed rather than certified.

This is where the zero_alloc annotation from the primer pays off, but be careful about how far the claim reaches. Roughly eighty hot-path helpers across the tape, parser, string, and number modules carry the annotation, so those stay allocation-free by construction as the code changes. What is not annotated is the composition: Tape.Parser.parse, the recursive stage-2 functions, and the scanner entry points carry no annotation, and -zero-alloc-check all means "check every annotation present", not "check every function". So the zero words per parse on every fixture is a measurement of the whole public operation, not a certificate for it. If someone asks how I know the difference: deleting the inline annotations produced a build that still passed the zero-alloc check and allocated about a hundred and nine thousand words per parse. Zero-allocation native parsing is possible—the checker just is not currently pointed at the whole of it. The tape aliases reusable buffers and is invalidated by the next parse. This is a diagnostic result and a useful borrowed API, not a like-for-like victory over a tree producer. [Sources] - docs/parser-benchmark-snapshot-2026-08-15.md - proposal.tex, Tape API

19 vs 8 is a count, not a time ratio: most of the extra work runs for free alongside the dependency chain. Micro-optimization is left here—which of it pays is not obvious from the source.

Now zoom into one representative scalar routine behind that 33-versus-15.8: the decimal-integer fast path, which accumulates one byte per iteration. Both loops load a byte, test whether it is a digit, and compute value = 10 × value + digit. These are exact loop bodies from the current x86 binaries on blue: C++ haswell DOM at 0x43d5ee and the inlined OxCaml scan_digits loop in Tape.parse_number_entry at 0x51be50. Cyan is parsing work. Orange is representation/control work: untagging positions and digits, updating a tagged index, and materializing the explicit end bound. Violet is the runtime poll. Two details worth having ready if someone reads the listing closely. First, the digit test: C++ subtracts '0' and does one unsigned compare against 9, so a byte below '0' wraps around and fails the same test; the OxCaml loop carries the digit tagged as 2d+1, so it needs a signed range check at both ends—the two cmp/jump pairs against 1 and 0x13. Second, the loop exit: instead of branching on the end bound where it is computed, setl and movzbq turn it into a 0-or-1 value in %rax, and the loop back-edge then tests that value. The test is not a redundant re-read; it is the branch that the materialized boolean forced to the bottom of the loop. Then land the caveat on the visible line, because it is the thought to carry into the lessons. Nineteen against eight is a count, not a ratio of times. This loop carries a serial dependency—value becomes ten times value plus digit—and the multiply alone is about three cycles of latency, so the bookkeeping instructions issue in its shadow on a wide out-of-order core and cost close to nothing. Our own checkpoints show it: unrolling the first scalar digit added instructions and gained the largest single throughput improvement in the number-parsing work, while removing instructions elsewhere gained little. So the honest position is that there is real micro-optimization left here, but which of it pays has to be measured rather than reasoned from the source. The other half, and the more useful half for this audience. Four of these are about expectations rather than missing features. Optimization decisions I would have assumed were automatic—inlining a tiny local helper, lowering an intrinsic to its instruction—had to be requested and then verified in the linked binary. simdjson's C++ design choices had to be ported as ideas rather than as code, and the most faithful rewrite of all, the explicit parser stack, was the one that lost. The popcount intrinsic lowered to a software helper and produced correct results eleven percent slower. The decisions are already reported: -inlining-report writes a per-round .inlining.org file covering every definition and every call site, with source spans, the estimated code size, the full cost-model parameter table, and a plain-English reason. It says "The function must be inlined at its use-sites because the function's body is smaller than the threshold size for small functions: size=66 <= large function size=100", and for a refusal, "The function cannot be inlined at its use-sites because the function's body is too large, more specifically, it is larger than the large function size: 500". There is also -flambda2-inlining-report-bin. On content that is richer than an LLVM remark, not poorer. So the ask is not observability, it is usability: a fourteen-line module with five functions produced a four-hundred-and-sixty-line report, most of it the same parameter table reprinted per entry. There is no misses-only mode the way LLVM has -Rpass-missed=inline, no way to rank by profile hotness the way -fdiagnostics-hotness-threshold does, and no viewer. That is why the disassembly route won. The lowering half of the ask has no equivalent anywhere—LLVM does not warn either when __builtin_popcountll silently expands to a twenty-instruction sequence because the target lacks popcnt. And the ask is not "raise the threshold" either—I measured that. With -O3 and the annotations deleted the parser loses eleven to twenty-eight percent and the zero-allocation tape path starts allocating about a hundred and nine thousand minor words per parse; -O2 and -O3 are otherwise a wash against the default build. A benefit estimate computed from the callee's own body cannot see that, which is why no preset substitutes for the annotation. Backup slide has the table. This is the answer to "did you just forget to turn on optimization?", and it is worth having ready because it is the first thing an optimizer person will ask. Three results. First, the annotations are load-bearing: delete them and the parser loses eleven to twenty-eight percent, worst on the number-heavy fixtures and on the tape path. Second, the preset itself is a wash—-O2 and -O3 land within about two percent of the default build either way, and the two are indistinguishable from each other, so the extra inlining depth in -O3 found nothing. Third, and most telling, allocation comes back: a path that reports zero words per parse starts allocating roughly a hundred and nine thousand minor words per parse. That third result is the real point, and the allocation profile says exactly where it comes from. Nearly all of it is number scanning: scan_digits, scan_integer and scan_exponent dominate the new allocation on both fixtures. Those functions deliberately return local, stack-allocated records—digit_run, integer_part, exponent_part—and the source relies on inlining to flatten that chain into the caller. Delete the annotations and Flambda2 does not reconstruct the flattened path, so numbers start bouncing between boxed and unboxed form across each call boundary: Int64_u and Float_u work on unboxed values, and a value that has to survive a real call gets boxed on the way out and unboxed on the way back. The flat representation survives only as long as the call disappears—which is why no threshold setting substitutes for the annotation. The fourth row is the follow-up experiment, and it separates two things the annotations were doing at once. Those five records were declared @ local but built without stack_, so they were heap blocks that merely satisfied a local mode—and the parser was allocation-free only because inlining removed them before they were ever built. Adding exclave_ stack_ to all five makes the allocation-free property hold by construction: zero words on both fixtures with every inline annotation still deleted, and the number-scanning hotspots vanish from the allocation profile. But the throughput does not come back—628 against 898, if anything slightly slower than the heap version on numbers.json. Inlining is not merely relocating those records, it is eliminating them by scalar replacement, and a stack region with entry, exit and a real call boundary still costs more than no record at all. Worth saying out loud: allocation-free is not the same thing as fast. Be straight about the zero_alloc question, because it is the obvious follow-up: how can an allocating build pass the check? Because -zero-alloc-check all means "check every annotation that is present", not "check every function". The annotations sit on leaf helpers—peek_index, the tape-word operations, the SIMD helpers, scan_block—and those remain allocation-free in isolation, so the check legitimately passes. Tape.Parser.parse, the recursive stage-2 functions, and the scanner entry points carry no annotation at all, so nothing certifies their composition. The accurate contract today is that the reusable tape path is empirically allocation-free with the project's inlining structure, not statically certified. The fix is available and worth stating as the ask: put [@zero_alloc opt] on an internal function spanning the whole successful hot path, and this experiment would have failed to compile instead of silently producing an allocating parser. This is the evidence behind the caveat on the assembly slide. Read the third row aloud: unrolling the first scalar digit retired more instructions than the checkpoint before it and produced the largest single throughput gain in the sequence, because it removed a loop back edge and its poll from the common post-SWAR tail. Meanwhile three billion fewer instructions across the whole sequence—about seven percent—bought roughly seven percent of throughput, so the coupling is weak and unreliable. The mechanism is the serial dependency: each digit needs the previous accumulator value, and the multiply is about three cycles of latency, so roughly four cycles per digit is the floor regardless of what else is in flight. Independent bookkeeping issues inside that window. If asked what would actually help: shorten the chain rather than the listing—split accumulation into two independent chains combined at the end, widen SWAR coverage so fewer digits go through the scalar tail at all, or remove more back edges.
